## 一、它是什么

一个 Windows 桌面程序：把钉钉群里机器人发的业务卡片（晚报、日报、积压提醒、
催提明细…）自动转到指定的微信群，并把卡片里挂的 Excel 附件作为**原文件**一起发过去。

- **来源**：钉钉群【数字质控】浙江杭州萧山区大江东公司
- **去向**：微信群「申通五星业务员培训群」
- **形态**：GUI 主程序 + 后台 worker + 安卓采集端 APK（三件套）

规模：核心 Python 约 **1.4 万行**（bridge + app），安卓 Java 约 **6300 行**，
测试 **64 个文件 / 1140 项**。

## 二、数据流

### 2.1 主链路

```
手机钉钉（APK 0.5.33，无障碍服务）
   │  ① POST /screen  每帧节点树 XML（画面变了才报）
   ▼
HTTP 网关 192.168.1.209:8765（android_gateway.py）
   │  ② 解析 → Unit 列表 → 与基线比对（锚点）→ 只留新增
   │  ③ 静默攒批（H5 卡片分批渲染，留最全的一版）
   ▼
BridgeService.handle()（service.py）
   │  ④ 去重 → 入库 → 自身通知过滤 → 积压闸门（30 分钟）→ 路由 → 模板渲染
   ▼
微信投递端（wechat_ocr.py，微信 4.x 走 OCR）
      ⑤ 找会话 → 粘贴 → 发送 → 表格补图 / 附件发原文件
```

手机端是**客户端**，只会主动连电脑（心跳 60 秒一次 + 有动作时抓帧），
电脑不能主动连手机 —— 所以所有「点击」指令都是挂在帧/心跳响应里带下去的。

### 2.2 附件支路

附件不跟正文同路：网关每帧扫消息里的附件行，自己维护一套订单队列。

```
网关扫到附件行（「明细附件：xxx.xlsx」/「查看完整…（Excel）」）
   │  记下这条消息的时间条（"今天 18:34"）+ 候选链（一张卡可能有好几行可点）
   │  fetch_attach 随帧下发给手机
   ▼
手机：按名字找行 → 精确滚动 → 无障碍点击 → 等文件落盘 → POST /file 回传
   │  失败就试候选链里的下一行；是钉钉原生预览页（只弹「转发另存/复制链接」）
   │  就 3~4 秒判定放弃，不占队列
   ▼
handle_attachment() → 换算源消息时间 → 走**同一道**积压闸门 → 发原文件
```

## 四、运行形态

### 4.1 两套目录（关键认知）

| 目录 | 角色 |
|---|---|
| `D:\wxauto-main\ddwx-bridge` | **开发目录**（改代码、跑测试、编译 APK） |
| `C:\Program Files\喵喵钉钉-微信消息转发桥` | **运行目录**（真正在跑的那份代码 + 独立的 config.yaml + 真库） |

⚠ 改开发目录**不会**影响正在跑的服务，必须同步到运行目录并重启。
两边 config.yaml 是**各自独立**的两份，不要整文件覆盖。

### 4.2 启停

- 停止：写运行目录的 `data/run.stop`，worker 会优雅退出（GUI 日志会显示「已停止」）。
- 启动：正常情况下点 GUI 的「开始运行」。
  ⚠ 已知问题：`PostMessage F5` 对 Tk 窗口不生效，GUI 里点不动时用命令行起：
  ```
  python app/bridge_worker.py --live --config <运行目录>/config.yaml \
      --stop-file <运行目录>/data/run.stop --parent-pid <GUI进程号>
  ```
  ⚠ 命令行起 worker 时 GUI 顶部仍显示「已停止」，**此时不能点「开始运行」，会双开**。

### 4.3 数据

- 真库：`C:\Program Files\喵喵钉钉-微信消息转发桥\data\bridge.db`
  （`messages` 消息表 / `deliveries` 投递记录表）
- 开发目录的 `data/bridge.db` 是 10-17 的旧库，看数据别看错。

## 五、七道防线（为什么它不容易出错）

1. **指纹 + uid 去重**：`storage.is_duplicate`；附件严一档 —— 必须**有成功投递记录**
   才算重复，否则重传时发不出去。
2. **锚点 + 基线**：只处理基线以下的新内容；锚点丢了先试探恢复，认输就回底重建。
3. **静默攒批**：H5 卡片分批渲染，按（群, 发送者, 时间窗）归并、留最长版本，
   静默 N 秒才发。宁晚几秒，不发残废消息。
4. **积压闸门**：源消息距今 > 30 分钟 → 只入库不转发（`MAX_BACKLOG_MIN`）。
   `force=True`（人工补发）和人工 `/attach-now` 豁免。
5. **附件四道**：名字冷却 → 失败退避 → 超时释放 → 候选链逐个试。
6. **投递补投**：失败延后 30 秒重试一次（uid 已入库，不补就永久漏）。
7. **自身通知过滤**：以系统前缀开头的运维文案不回灌到微信群。

## 六、配置全景（config.yaml 五段）

| 段 | 项数 | 要点 |
|---|---|---|
| `storage` | 1 | `db_path` |
| `dingtalk` | 21 | `mode`（当前 `android`）、`chat_names`、附件字眼、抓取开关、网关端口/token |
| `wechat` | 15 | `dry_run`、发送间隔与随机长停顿、`driver`（auto/wxauto/ui4/ocr）、附件临时改投 |
| `notify` | 17 | 钉钉机器人告警：冷却、触发条件、闲置判定、运行报告 |
| `routes` | 1 条 | 一条规则 = 一个钉钉群 → 一个/多个微信群 |

路由匹配是**四个维度依次过滤**：`companies` / `chat_names` / `msg_types` / `keywords`，
空列表 = 不限。当前只按 `chat_names: ["数字质控"]` 匹配。

## 八、技术债与风险清单

按「会不会咬人」排序。

### 🔴 P0：大量改动没有提交

最后一次 git 提交是 **2026-10-29 21:08（APK 0.5.20）**，之后：

- **30 个已修改文件未提交**（含 gateway / service / config / 安卓 5 个类）
- **24 个未跟踪项**（含 `phone_panel.py`、多个新测试、6 个 APK）

也就是说 0.5.21 → 0.5.33 的全部工作 + 今晚的服务端改动**只存在于工作区**。
一次误操作（回滚、清理、换机器）就全没了。

### 🟠 P1：安卓端「翻屏不生效」

0.5.33 真机状态一直报：

```
翻屏：上翻第1屏:工作产物,上翻第2屏:工作产物,上翻第3屏:工作产物…
```

每屏首行都是同一个固定 UI 节点，说明 `firstText()` 取错了节点，
「滚了没滚」的判断依据是假的 —— 精确滚动的收敛逻辑等于在没有反馈的情况下瞎滚。
影响：目标行不在首屏时找不到（今晚补抓 18:34 晚报明细就卡在这）。
影响有限的原因：新消息到达时卡片本来就在屏底，不走这条路。

### 🟠 P1：钉钉原生预览页拿不到文件

「明细：xxx」这类蓝链接点开的是钉钉自绘预览页，整页不在无障碍树里，
「下载」只弹「转发另存 / 复制链接」，没有落盘入口。0.5.33 已做成 3~4 秒快速放弃，
但**这一类卡片就是拿不到原文件**（不是 bug，是对方没给口子）。

### 🟡 P2：仓库里的垃圾与重复

| 目录 | 体积 | 说明 |
|---|---|---|
| `tmpd/` | **175 MB** | 历史 payload 快照、旧备份、smoke 副本 —— 全是死物 |
| `installer/` | **101 MB** | 含 `_build/payload` 的整份代码副本 |

整个工作目录 **438 MB**，其中真正在用的代码不到 5 MB。
`tmpd/` 里还有好几个 `android_gateway.py` 副本（3561 行），
搜索/替换时极易改错文件 —— 这已经不是整洁问题，是**改错文件的风险**。

### 🟡 P2：文档与实现脱节

- `README.md`（48 KB）：大量篇幅在讲钉钉 OCR 截屏方案、三道防线，

- 新接手的人按文档理解，会得到一套已经不在跑的架构。

### 🟡 P2：`driver: auto` 的隐式降级

auto 探测到 ui4 会**静默**换成 OCR，只在日志写一行。这本身是对的
（4.x UIA 已废），但写在 `targets/__init__.py` 的文档字符串里，
排查投递问题的人通常不会翻到这里。

## 九、日常运维速查

| 要看什么 | 怎么做 |
|---|---|
| 服务活着吗 | `curl -H "X-Bridge-Token: <token>" http://192.168.1.209:8765/ping` |
| 手机什么版本、在哪个群 | 同上，看 `app_ver` / `chat_name` / `last_seen` |
| 附件在抓什么 | 同上，看 `attach_active` / `attach_queue` / `attach_pending` |
| 附件为什么没抓到 | 看 `attach` 字段（手机会把失败原因原样上报） |
| 某条为什么没转发 | 查 `deliveries` 表按 uid；或看日志的「积压超龄 / 未命中规则 / 重复跳过」 |
| 补发历史消息 | `tools/forward_recent.py`（`force=True`，跳过去重与闸门） |
| 手工补抓附件 | `POST /attach-now?name=<屏上那行的原文>`（豁免积压闸门） |

⚠ 网关是 `192.168.1.209:8765`，**不是** `127.0.0.1:8765`（后者被别的 http.server 占着）。

## 十、一句话总结

主干（`android_gateway` → `service` → `wechat_ocr`）是稳的，防漏防重的机制很密；
真正的问题是**工程卫生**：53 处改动没进版本库、175 MB 死物与活代码混在一起、
文档描述的是三个月前的架构。这三件事的修复成本都不高，但拖着的代价在放大。
