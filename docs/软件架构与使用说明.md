## 一、它是什么

一套常驻 Windows 的转发程序：**把钉钉群里的消息，实时、原样地转发到指定的微信群**。

当前生产实例：

| 项 | 值 |
|---|---|
| 消息来源 | 钉钉群「数字质控·大江东」 |
| 转发目标 | 微信群「申通五星业务员培训群」 |
| 采集方式 | 安卓手机无障碍读屏 → 局域网 POST 给电脑 |
| 投递方式 | 微信 4.x UIA 控件操作（剪贴板粘贴 + 回车） |
| 部署位置 | `C:\Program Files\喵喵钉钉-微信消息转发桥\` |

解决的核心痛点不是「跨平台发消息」这么简单，而是三件事：

1. **拿得到** —— 钉钉群消息没有合规的开放接口可读（企业开发者权限 + 内部应用 + `Chat.Message.Read` + 发布版本，四者缺一不可），只能走「终端读屏」。
2. **不重复、不遗漏** —— 群消息会滚动、卡片会重绘、长消息会被屏切断，程序必须自己判断「哪条是新的」。
3. **坏了有人知道** —— 这类程序最怕静默失效（窗口被切走、手机被清理），所以配了钉钉机器人告警。

### 2.2 进程模型：为什么是两个进程

程序**不是**单进程。GUI 与业务逻辑跑在两个不同的 Python 解释器里，用管道通信：

```
喵喵钉钉-微信消息转发桥.exe   （PyInstaller 打包，内置 tkinter）
        │  app/gui.py —— 只管界面、按钮、日志着色、统计刷新
        │
        └─ subprocess ──▶ app/bridge_worker.py
                          （用「工作解释器」跑，带 comtypes / rapidocr / yaml）
                          真正的采集、解析、投递全在这里
```

原因很实际：

| 进程 | 解释器 | 必须有的依赖 | 缺了会怎样 |
|---|---|---|---|
| GUI | 系统 Python 3.12（`%LocalAppData%\Programs\Python\Python312`） | tkinter | 窗口打不开 |
| Worker | `~/.workbuddy/binaries/python/envs/default` | comtypes（UIA）、rapidocr/onnxruntime（OCR）、PyYAML | 投递全废 / OCR 不可用 |

两个解释器缺的依赖正好互补，所以**不能合成一个**。GUI 启动时会自动探测（`app/paths.py`），探测结果缓存在 `app/_env.json`；换机器或装新依赖后可点「重新检测运行环境」。

> 排查铁律：跑程序用 **worker** 解释器；跑单元测试用 **Python312**（worker 没装 tkinter，5 个 GUI 用例会报 `ModuleNotFoundError`，那不是真失败）。

### 2.4 采集端：四条路，只有一条通

| 模式 | 原理 | 现状 | 关键限制 |
|---|---|---|---|
| `android` | 手机无障碍读整屏节点树，POST 给电脑 | **当前生产在用** | 需一台常亮安卓机；屏灭 = 采集停 |
| `ocr` | 电脑截钉钉窗口 → PP-OCR 识别 | 备用 | 钉钉窗口必须在前台且不被遮挡；一帧约 2.5s |
| `stream` | 钉钉官方事件订阅 | 未采用 | 需企业开发者权限；且**只收得到 @机器人 的消息** |
| `ui` | 读钉钉 PC 控件树 | 已证伪 | 钉钉是 CEF/DUI 自绘，消息区不在无障碍树里 |
| `probe` | 只探测不采集 | 诊断用 | — |

已排除的更彻底的路子：**群管理员身份对读消息零帮助**（钉钉接口授权是应用维度）；**本地缓存库全加密**；**webhook 只能发不能收**。

### 2.5 投递端

| 驱动 | 适用微信版本 | 实现 |
|---|---|---|
| `wechat4`（默认） | 微信 4.x（实测 4.1.15.13） | 按 `mmui::` 控件名操作：搜会话 → 剪贴板 `Ctrl+V` → 回车 → **回读校验** |
| `wechat` | 微信 3.9.x | wxauto 原版逻辑（该项目已于 2025-10 归档） |

`wechat.driver: auto` 会自动探测本机微信代际。投递端的三个可靠性设计：

- **绝不按 Esc**：微信 4.x 里搜索面板之后按 Esc 会把主窗口收进托盘，窗口对象从 UIA 树消失。
- **`ensure_visible()` 三态恢复**：最小化 → `SW_RESTORE`；收进托盘 → 按窗口句柄 `SW_SHOW`；热键 `Ctrl+Alt+W` 只作兜底（它是开关，隐藏时唤不回）。
- **发送后回读**：读不到刚发的文本就算失败，写进 `deliveries` 表并触发告警。

### 2.6 核心数据结构

一条消息的 `uid` 决定一切（幂等键）：

```
android:4331de090dc165ae26c3192a8f389c92:1
└─来源─┘ └────── 内容指纹（16字节）──────┘ └序号┘
```

指纹由 `bridge/fingerprint.py` 统一生成，**OCR 通路与安卓通路共用同一份实现**——两边各写一份会导致同一发送者两种写法、两个 uid，换采集方式后旧消息全部重发。测试 `TestNoDriftBetweenPaths` 用 `assertIs` 锁死这一点。

### 2.7 防重与防漏：六道机制

这是本项目最复杂的部分，也是历史 bug 最集中的地方。

| 机制 | 解决什么 | 代价 / 边界 |
|---|---|---|
| **首帧建基线** | 程序刚启动时不把整屏历史灌进群 | 启动瞬间那一屏不发 |
| **锚点（上一帧最后一条）** | 只转发锚点之后的内容，滚动看历史不会误发 | 锚点对不上就整帧不发 |
| **锚点近似匹配** | 卡片重绘导致字面变化 → 精确匹配失效 | 只认「片段集合完全相等」，短消息（<30 字）不参与 |
| **锚点丢失先翻屏试探** | 长消息把锚点挤出屏外，手动上翻又能转 | 最多试 2 次，间隔 3 秒，失败才重建基线 |
| **锚点上方新增判定** | 机器人卡片渲染完插到通知**上面**，`idx+1:` 永远为空 | 判据极保守：上方只有一条 + 贴列表上沿 + 紧贴锚点 |
| **H5 卡片扣住待稳** | 卡片分批渲染，抓半成品会丢表格 | 坏坐标文本节点 ≥4 才扣，最多扣 4 眼 |
| **投递口近似去重** | 同一卡片换形态 → 新 uid → 重复发 | 窗口 600 秒，集合完全相等才判重 |

> 为什么「近似」的阈值必须是最紧的「集合相等」而不是重合度：表格改一个数字（93.33%→88.10%）时重合度仍有 97%，按 90% 判重会把隔天日报吃掉 → **永久漏发**，比多发严重得多。

## 三、功能清单

### 3.1 自动转发

- 从采集端拿到新消息 → 判重（数据库）→ 落库 → 规则路由 → 模板渲染 → 限流（默认 3 秒/条）→ 投递 → 记录投递结果。
- 一条消息可以同时投递多个目标（同一规则多个 targets，或多条规则命中合并去重）。
- 投递失败重试不自动，但会连续 3 次失败后告警。

### 3.2 规则路由

`routes` 从上到下依次匹配，**命中的目标合并去重**，模板取第一条命中的：

| 条件字段 | 匹配方式 | 空值含义 |
|---|---|---|
| `companies` | 不区分大小写的**包含**匹配 | 不限 |
| `chat_names` | 同上 | 不限 |
| `keywords` | 对正文做包含匹配 | 不限 |
| `msg_types` | `text` / `image` / `file` / `voice` / `link` | 不限 |
| `targets` | 微信里的群名或好友备注，**必须完整一致** | 必填 |
| `template` | 见下 | 用默认模板 |

模板占位符：`{company}` `{sender}` `{chat}` `{time}` `{content}` `{type}`
默认：`【{company}】{sender}：\n{content}`

### 3.3 手动补发

界面「工具 → 转发最近 N 条（预览后确认）」，或命令行：

```bash
python tools/forward_recent.py                    # 预览最近 3 条（抓钉钉当前画面）
python tools/forward_recent.py -n 5 --ask         # 预览 5 条，逐条确认
python tools/forward_recent.py --from db --ask    # 从已入库记录补发
```

用途：手机掉线、程序没在跑、某条被过滤掉之后补回来。`force=True` 只跳过去重，投递记录照记（补发过的事实留在库里，不会被下次统计重复计数）。

### 3.4 告警与运行报告（钉钉机器人）

机器人 webhook 是**单向**的（只能往群里发，收不到群消息），它不参与取数，只负责「出问题主动喊人」：

| 场景 | 触发条件 | 配置项 |
|---|---|---|
| 启动 / 停止 | 点开始、点停止各一条 | `notify_start` |
| 投递连续失败 | 默认连续 3 次 | `notify_fail` / `fail_threshold` |
| 采集停滞 | 120 分钟没有新消息（仅 08:00-21:00 判） | `notify_idle` / `idle_minutes` / `idle_window` |
| 手机失联 | 心跳断 5 分钟（0.2.0 起有心跳） | `android_offline_after` |
| 采集端异常日志 | 窗口找不到、最小化等 | `log_alerts` |
| 定时报告 | 每小时 / 每天指定时刻 | `report_hourly` / `report_daily_at` |

- 同类告警默认 5 分钟内只发一次（`cooldown`），防刷屏。
- 支持**多个机器人**（一行一个，各自带加签密钥/关键词），一个成功即算成功。
- 程序自己发出的运维通知带 `【系统】` 前缀，采集端读到后**只入库不投递**——否则「转发桥已启动」会被转进微信业务群（真发生过）。

### 3.5 记录与导出

- 「工具 → 消息记录」：按时间倒序看入库消息与投递状态。
- 「导出 CSV」：UTF-8-BOM，Excel 直接打开。
- 统计：本次运行的识别/投递/失败/跳过 + 累计入库与投递数。

### 3.6 桌面集成

- 开机自启（写注册表 `Run` 项，设置中心可开关）。
- 桌面/开始菜单快捷方式：`python app/setup.py`（`--remove` 卸载，`--quiet` 静默）。
- 试运行模式：`wechat.dry_run: true` 时只在日志里打印不真发，顶部有黄色提示条。

## 四、安装与首次配置

### 4.1 装电脑端

1. 运行 `installer/dist/喵喵钉钉-微信消息转发桥-Setup.exe`（约 24.7 MB），装到 `C:\Program Files\喵喵钉钉-微信消息转发桥\`。
2. 启动程序 → 首次会**自动生成** `config.yaml`（样板来自 `config.example.yaml`）并做一次只读自检。
3. 「设置 → 设置中心」把事情配完，点右下角「保存」（原配置自动备份到 `data/backup/`）。

升级安装**不会覆盖** `config.yaml` 与 `data/`，只补缺失的配置段；段内新增的键用 `tools/ensure_config_keys.py` 补。

### 4.2 必填的三件事

| 项 | 在哪里 | 说明 |
|---|---|---|
| 转发目标 | 设置中心 → 转发规则 | 微信群名必须与客户端完全一致 |
| 微信热键 | 采集与投递 | 默认 `Ctrl+Alt+W`，改过微信快捷键就要跟着改 |
| 网关 token | 设置中心 → 采集与投递（或 config.yaml `dingtalk.gateway_token`） | **不填程序直接拒绝启动**：能往这个端口 POST 就等于能往你的群发消息 |

生成 token：

```bash
python -c "import secrets;print(secrets.token_urlsafe(24))"
```

### 4.3 装手机端

1. 手机浏览器打开 `http://<电脑IP>:8765/app`（局域网），页面上印着 IP / 端口 / token，可直接下载 APK。
2. 安装后**授予无障碍权限**（设置 → 无障碍 → 已安装的服务 → 「喵喵采集端·读钉钉」）。
3. App 首页填电脑 IP、端口、token → 保存 → 点「测试连通性」应显示「✔ 通了」。
4. 打开钉钉进入目标群 → 切回 App 看「读到文本 N 条」「已上报」「心跳 ✔ 正常」。
5. 设置页底部两个按钮都点一遍：允许后台常驻、启动管理改为「手动管理」。

**保活四层，缺一层就会静默失效**（详见 `android/README.md`）：

| 层 | 做法 | 能解决 / 不能解决 |
|---|---|---|
| 屏幕不灭（决定性） | 开发者选项 →「保持唤醒状态」+ 一直插电 + 不按电源键 | 实测屏灭后心跳当场断、8 分钟不恢复；这是厂商灭屏挂起，不是 Doze |
| 常驻通知 | App 自带前台服务，30 秒查一次无障碍 | 掉线只**提醒**，不能自动重开（需 `WRITE_SECURE_SETTINGS`） |
| 启动管理 | 关「自动管理」，允许自启动/关联/后台；任务栏加锁 | 防厂商省电清理 |
| 心跳 | 每 60 秒 `POST /ping` | 让电脑能区分「没人说话」和「手机死了」 |

> ⚠ 别手动清后台、别重启后不管：华为清理或重启后**无障碍开关会自己变关**。重启后第一件事是确认它还在开。

### 5.2 每天的标准动作

1. **打开程序**（双击桌面快捷方式）→ 等状态灯变绿。
2. **点「自检」**：确认「投递端 wechat4 可用 / 采集端监听 0.0.0.0:8765」。
3. **点「▶ 开始运行」→ 弹框点「是」** —— 这一步才真正开始采集。
   > 自检只是**预检，不监听端口**。看到「采集端：通过 — 监听 0.0.0.0:8765」不代表在跑，必须点开始。
4. **确认手机端在报**：日志出现「收到第一帧手机画面…（来自 PAL-AL00）」。
   第一帧**只建基线，一条都不转发**，这是设计如此。
5. 下班点「■ 停止」，或直接关窗口（会写 `data/run.stop` 让 worker 退出）。

```yaml
storage:

  mode: "android"                  # android | ocr | stream | ui | probe

wechat:
  dry_run: false                   # true = 只打印不发
  interval: 3.0                    # 相邻发送最小间隔，防风控
  driver: "auto"                   # auto | ui4 | wxauto
  targets: []                      # 兼容老配置；实际目标看 routes
  show_hotkey: "{Ctrl}{Alt}w"

notify:
  enabled: true
  webhooks:
    - "https://oapi.dingtalk.com/robot/send?access_token=xxx | SECxxx | 关键词"
  cooldown: 300
  fail_threshold: 3
  idle_minutes: 120
  idle_window: "08:00-21:00"
  report_daily_at: ""              # 例如 "18:00"

  - name: "默认"
    companies: []
    keywords: []
```

## 八、排障速查

| 现象 | 先查什么 | 常见原因 |
|---|---|---|
| 微信没收到 | `deliveries` 表 status=fail 的 error | 微信没登录 / 群名不一致 / 窗口被弹窗挡住 |
| 手机连不上 | `netstat -ano \| findstr :8765` | **电脑侧没点开始运行**（自检不等于在跑）；防火墙；不在同一 WiFi |
| 在跑但一条不转 | 日志有没有「锚点丢失」 | 锚点对不上会静默重建基线；卡片渲染形态变化 |
| 某条就是没有、日志全绿 | 抓帧看它是不是在锚点**上方** | 机器人卡片插到通知上面，老逻辑只看下方 |
| 重复转发 | `deliveries` 里同内容不同 uid | 卡片换形态；近似去重窗口 600 秒之外的复现 |
| 手机失联没告警 | 心跳有没有到 | 旧版 APK 无 `/ping`；`android_offline_after` 设了 0 |
| 屏灭了以后全丢 | 手机是否在充电、是否按了电源键 | 厂商灭屏挂起，前台服务保不住 |
| 8765 端口起不来 | 有残留 worker 占着端口 | 跑 `停止后台程序.bat` |
| 设置保存后启动失败 | 老配置缺新键 | `python tools/ensure_config_keys.py` |

排障工具：

```bash
python tools/android_screen.py --token xxx        # 看手机报上来的最新一帧
python tools/android_capture.py                   # 只收不转，验证手机会报
python tools/android_gateway_selftest.py --token x  # 无手机验通电脑侧（不碰微信）
python tools/android_offline_selftest.py          # 验证失联告警真的会响
python tools/probe_anchor_stability.py            # 逐帧看锚点存活
```

### 9.3 改代码的三条硬约束

1. **配置写入**：新增配置项必须用 `set_or_insert_scalar` / `ensure_list_key`，插入行**必须带段内缩进**（丢缩进会变顶层键，误删后续配置）；同时同步 `config.example.yaml` 和 `settings_ui.save()`。
2. **界面布局**：底部固定按钮栏必须**最先** `pack(side="bottom")`，否则会被内容挤成 0 高（保存按钮消失过一次）。
3. **`.bat` 文件**：必须 GBK + CRLF + 纯 ASCII 语法，别经 shell 拼含引号的命令。

## 十、已知限制与风险

| 限制 | 影响 | 缓解 |
|---|---|---|
| 手机屏灭即停采 | 灭屏期间的群消息**全部丢失**，且不报错 | 保持唤醒 + 常亮 + 插电；靠心跳告警发现，恢复后手动补发 |
| 微信 UIA 暴露可能被关 | 某天微信改版后投递全废 | 微信大版本升级后先跑「自检」；`tools/probe_wechat_ui.py` 提前发现 |
| 微信风控 | 短时间大量发消息可能被限 | `wechat.interval` ≥3 秒；不用于营销群发 |
| 电脑钉钉 OCR 会丢表格右半边 | 补发的正文不完整（实测 389 字 vs 手机 814 字） | **补发优先用手机抓帧**，电脑版只当「消息存在」的证据 |
| 钉钉安卓无障碍可能被系统收紧 | 新版钉钉若改自绘，解析会失效 | 解析器按页面布局 id 链判定，先 `detect_page` 再解析 |
| 合规 | 转发的是内部业务群消息 | 只在内网、只转自有群；不对外分发 |

## 附：术语

| 词 | 含义 |
|---|---|
| 基线 | 程序启动时「当前屏幕最后若干条」，之后只转它之后的新内容 |
| 锚点 | 上一帧的最后一条消息，用来切分「新/旧」 |
| 帧 | 手机上报的一次完整屏幕节点树（XML） |
| 卡片 | 钉钉机器人发的 H5 富文本消息（表格、多段），渲染分阶段 |
| 扣住 | 判定卡片还在渲染，先不发，等下一帧一致了再发 |
| 试探 | 锚点丢失时请手机翻一屏找回，而不是直接重建基线 |
| 系统消息 | 程序自己发的运维通知，带 `【系统】` 前缀，只入库不投递 |
